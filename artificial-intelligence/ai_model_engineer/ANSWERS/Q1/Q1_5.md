# Q1.5 — MLOps infrastructure design

A high-level MLOps design for managing this system would cover the following areas:

1. **Code and data versioning:**
   - I would use Git for the training codebase and DVC (Data Version Control) for the image datasets. This ensures reproducibility — we always know which data was used to train each model version.

2. **Training pipelines (CI/CD):**
   - I would set up GitHub Actions to automate the training pipeline: when the dataset or model code is updated, a workflow triggers training, evaluation, and validation automatically.
   - Regression tests would compare the new model's metrics against the previous version before approving the release.

3. **Model registry:**
   - I would store trained model versions with their metadata: metrics, dataset used, training date, and parameters.
   - MLflow is the standard option for this purpose.

4. **Deployment:**
   - The model would be packaged in a Docker container and served as an API (FastAPI or similar).
   - For real-time video inference, the model can be embedded in the application via ONNX, which allows framework-agnostic and optimized inference.

5. **Production monitoring:**
   - I would monitor data drift (whether incoming images change distribution compared to the training data) and performance drift (whether accuracy degrades over time).
   - Alerts would be triggered when the model degrades, which can initiate a retraining cycle.

6. **Retraining loop:**
   - An automated or semi-automated pipeline: new data arrives → retrain → evaluate → if it improves, promote to production; if not, discard.

The overall goal is to have a reproducible, auditable, and automated lifecycle where every model in production is traceable back to its data, code, and training configuration.
