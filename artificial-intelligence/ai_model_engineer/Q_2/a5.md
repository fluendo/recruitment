# Question 5 — Proposed Model

**My proposal:** RTMPose-s for pose (with a small person detector and a tracker)
and a small temporal CNN on the keypoints for the hits. I'd also try a small
ST-GCN and keep it only if it clearly beats the CNN. Both are light, and the
pose model comes pretrained.

## Pipeline overview

```
video -> person detection + tracking -> 2D pose (per player) -> keypoint smoothing
      -> feature extraction -> windowed hit model -> event merging
```

The pose model is the dominant computational cost. The hit model and the
post-processing are small. Each of the four players is processed independently
through tracking.

## Pose model: RTMPose

RTMPose comes from MMPose (OpenMMLab). I'd use the small variant, RTMPose-s.

- **Why**: real-time inference, good accuracy and consistent keypoint placement,
  and it is available pretrained at no training cost.
- **Detector and tracker**: RTMPose is top-down, so it needs a person detector
  (RTMDet-tiny). A tracker follows each player over time. I'd limit the detector
  to a court region of interest, to ignore spectators and neighboring courts.
- **Fine-tuning**: I'd validate the pretrained model and fine-tune it on padel
  footage from several clubs and camera setups (Q1), using the cleaned
  annotations from Q2.
- **Smoothing**: temporal smoothing (One Euro or Kalman filter) removes keypoint
  jitter at almost no cost (Q4). I tune it so it does not flatten fast wrist
  motion.
- **Speed**: I measure the speed of the full pipeline (detection, tracking, pose,
  hit model) on the target hardware. If it is not fast enough, I'd try the tiny
  variant (RTMPose-t) or a lower input resolution.

## Hit model: temporal CNN baseline, ST-GCN as a possible upgrade

**Baseline**: a small temporal convolutional network (TCN) on the same features
(see below). With 17 joints and short windows it often performs similarly to a
graph network, and it is simpler to export and run in streaming. I keep the
graph network only if it beats this baseline in the evaluation protocol of Q1 to
Q4.

**Possible improvement**: a graph neural network in the ST-GCN family takes the
skeleton as a graph: the joints are nodes and the bones are edges, with temporal
connections across frames. The skeleton structure is a natural inductive bias,
which should help data efficiency for rare classes such as smashes. I'd keep the
network small (a few layers) to respect the compute constraint. Implementations
exist in MMAction2, from the same OpenMMLab family as MMPose. I'd train it on our
own features, since its pretrained checkpoints come from action datasets such as
NTU and FineGYM, not from padel. I'd also check that our input format works with
this type of network, since we compute extra information beyond the keypoint
positions themselves.

### Input features (per node and per frame)

- Positions normalized to the torso center and torso length, which gives
  position and scale invariance. Viewpoint robustness comes mostly from the 3D
  reprojection augmentation (Q3).
- Velocity and acceleration, computed on smoothed keypoints, in normalized units
  and per second so that they do not depend on the frame rate.
- Joint angles (elbow, shoulder) and bone vectors.
- Wrist height relative to the shoulder and head, which separates smashes (wrist
  above the head) and serves (wrist around the waist) from the other hits.
- Keypoint confidence, so that uncertain joints are down-weighted.
- Hip-center velocity, normalized by torso length and expressed per second. It
  restores the global motion that the torso normalization removes: running to
  the ball, the split-step before a volley, the jump of a smash.

The angles and heights are measured in 2D, so they still depend on the camera
view. The viewpoint augmentation from Q3 is what keeps them reliable across
clubs.

### Optional features

- **Court position** (distance to the net, court side) requires a court
  homography: a one-time click on four court corners per fixed camera, or a
  small automatic court-line detector. It makes this feature independent of the
  camera, at the cost of a calibration step and its errors. I'd include it only
  if an ablation shows a gain that justifies the cost.

## Temporal window and output

- The window is sized in **seconds**: around 1 s, covering a full swing, with
  roughly 0.2 to 0.3 s of future context after the **target frame** (about 0.75 s
  of past and 0.25 s of future). The prediction refers to the target frame, so
  the output is delayed by that amount. This is acceptable unless the product
  requires real-time feedback.
- If the delay is not acceptable, a causal variant uses only past frames and
  predicts for the current frame (expect lower accuracy).
- The model predicts per frame over overlapping windows, with an additional
  background class for non-hit frames. Peak picking or non-maximum suppression
  merges the overlapping predictions, so that each hit produces a single event.
- Training uses soft labels around the annotated frame, which matches the
  timestamp noise discussed in Q2.

## Training and evaluation

- Class weighting, hard negatives and threshold adjustment for smashes.
- Keypoint-space augmentation and 3D lifting with reprojection to new camera
  views.
- Evaluation split by match and club, with per-class metrics, event-level
  metrics and timing error.
