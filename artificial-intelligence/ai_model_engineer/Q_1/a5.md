# Question 5: MLOps Infrastructure Design

## 1. Data Layer

Raw images and annotations are stored in an S3 bucket (named per
org/project), with one folder per split plus a folder for the
attribute-labelled evaluation set from Questions 3-4. DVC versions
this data on top of S3: it tracks a folder by content hash,
and uploads only the new or changed content to the S3 remote.
This way a git commit now pins an exact dataset hash, so any model
can be traced back to the data it was trained on, updates only cost
the size of what actually changed, and an earlier version can be
restored on demand.

A per-sample metadata table (image id, split, subgroup labels such as skin
tone and baldness, bbox info, dataset version) is generated from the raw
data as its own DVC pipeline stage, so it only regenerates when the
underlying split actually changes. This one table is used in two ways.
data-profiling summarizes it into a per-split report on subgroup balance 
and distribution skew. The same table, loaded into a queryable database, 
is what SQL is used for: querying it to pull out the subgroup evaluation 
sets from Q3-4 (e.g. all bald and dark-skinned images), and to compute 
bias/skew statistics per group.

Profiling outputs two files: an HTML report for a person to read, and a
small JSON/CSV file with the same numbers in a structured form, so a CI
pipeline can check them automatically instead of relying on someone
reading the report before every promotion.

Synthetic data (the rendered/generated bald-face samples from Question 3)
is generated offline, as its own DVC pipeline stage producing a versioned
artifact pushed to S3. It's expensive to generate and needs to be
inspected for domain gap before use, so it's treated as data and not
regenerated at training time.

## 2. Training Layer

Model code is built in PyTorch, using HuggingFace Transformers/Datasets
for any pretrained backbone, and OpenCV/Albumentations for preprocessing.
The cheap, parametric augmentation from Question 3 (exposure/gamma/
contrast, occlusions) runs online here, freshly randomized every epoch. It is
versioned as code and config, not as stored images like the synthetic
data from the data layer. A run is fully specified by a config file, the DVC
data version, the git commit and the Docker image from section 5, so it can be
reproduced from those. MLflow logs each run's parameters, metrics, losses and
artifacts.

Hyperparameter search (learning rate, augmentation strength, and the
detection/embedding loss weight from Question 1) runs with Optuna inside Ray
Tune. Optuna's sampler picks the next configuration to try based on previous
trials' results, and Ray Tune distributes the trials across a cluster, if available,
and stops clearly bad ones early. Each trial logs to MLflow as its own run.
The objective is worst-group recall at a fixed false-blur rate (or a
combination with the overall metric), not just the overall metric. This turns
the acceptance criterion from Questions 3-4 into something the search
actually optimizes for. The confidence threshold is not part of the search: it
is set after training from the worst-group recall target, as in Question 3.

## 3. Evaluation Gate and Model Registry

After training, the model is evaluated on the subgroup-labelled eval set
from the data layer, producing overall and per-subgroup recall (Questions
3-4). A model is promoted only if it clears a fixed floor (e.g. worst-group
recall above a set target) and is not worse than the model currently in
production. The results are written to a JSON file next to the HTML report,
the same pattern as the data profiling, so CI can check the gate
automatically instead of relying on someone reading a report.

MLflow's Model Registry enforces the result with aliases (`staging` and
`production`). A trained model is registered with its DVC data hash, git
commit, config, and a link to its evaluation report, so any version can be
traced back to exactly what produced it, as the AI Act asks.
The gate decides the promotion: a model that fails the criteria is not given
the `staging` alias, and the failure report (which subgroup, by how much) goes
directly to the Question 3-4 diagnostic process. A model that passes gets the
`staging` alias automatically. Moving to `production` stays a human-approved
step: bad models are auto-rejected, but nothing is auto-deployed without a
person confirming, given the compliance stakes of a system that processes
biometric data.

## 4. Optimization and Export

A promoted model is quantized (post-training quantization by default,
quantization-aware training only if accuracy drops too much) and pruned
(structured, so channels/filters actually drop rather than needing sparse
kernels most GPUs don't accelerate). It's then exported to ONNX, checked
for numerical parity against the PyTorch model, and compiled to a
TensorRT engine for the target GPU. The engine is a build artifact tied
to a specific GPU architecture and TensorRT version, and it carries a
reference back to the registered model version it was built from, same
lineage principle as the rest of this design.

Numerical parity on average outputs isn't enough sign-off, though:
compression is known to hurt minority subgroups more than the overall
metric. This matters here specifically because Questions 3-4 already
found some subgroups sitting close to the confidence threshold. 
So the quantized/exported artifact goes back through the evaluation gate
from section 3, re-checking subgroup recall, rather than being signed off
on the original float32 checkpoint's results alone.

## 5. CI/CD

GitHub Actions runs the pipeline. Docker containerizes the CI runner
environment so a pipeline run doesn't depend on whatever happens to be 
installed on the runner. That image is versioned alongside the data hash, 
git commit and config, so the whole run can be reproduced (data, code, 
config and environment are all pinned together).

On a pull request, the pipeline runs lint and the pytest suite (including
the config-driven pipeline tests). On a change that affects the model, it
also triggers the evaluation gate from section 3, and builds/pushes the
Docker images: a slim inference image and a full training image, kept
separate since only the former needs to ship to production.

## 6. Deployment and Serving

GStreamer is the multimedia pipeline framework the actual video processing
graph runs on: decode the stream, run the detection and depth elements,
composite the blur, encode/output. The exported ONNX/TensorRT model from
section 4 is wrapped as a GStreamer element inside that graph, so inference
stays in the pipeline. The graph is set up from a YAML config file (which
elements run, blur style and intensity), and the presets from Question 6 are
saved versions of that file.

## 7. Production Monitoring

Live input/output distributions are compared against the training
distribution on a schedule, generating the drift reports. They should
flag drift (camera, lighting, scene changes) that would warrant retraining or
re-tuning. Operational numbers are collected too (FPS, latency, GPU
usage), and a visualization tool can be used to show them and sends alerts. 
Separately, the subgroup evaluation from section 3 is re-run periodically 
to check the model keeps performing on the subgroups Questions 3-4 identified as weak.

One problem: there's no ground truth on live video by default, so this can't
run against automatically-inferred subgroup labels without introducing a new
instance of sensitive biometric processing (Question 1's concern) just to
power a monitoring dashboard. Instead, **manual audit sampling** runs
periodically: a small, scheduled sample of production frames, hand-labelled
for the subgroup attributes and run through the same evaluation-gate metric.
This is the one exception to the "nothing is stored" rule, so the sampled 
frames are handled as sensitive data: a small sample, access limited to the 
reviewers, and deleted once labelled.
