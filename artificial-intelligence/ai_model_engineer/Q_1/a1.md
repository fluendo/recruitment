# Question 1: Adding Reidentification to Selective Face Anonymization

## Architecture: shared backbone, conditional embedding head

Rather than running a second, independent CNN on every detected face crop, the
detector's backbone is reused as the feature source for identity embeddings.

- **Detection head**: unchanged from the existing YOLO-style detector.
  Produces face bounding boxes per frame as before.
- **Embedding head**: a new, lightweight head added on top of the same
  backbone feature maps. For each detected box, features are taken 
  directly from the already-computed feature maps (no re-encoding of
  the raw crop) and projected to a low-dimensional embedding (128-d, or lower;
  64-d is workable). 

The embedding head is trained with a **metric-learning loss** (ArcFace
or CosFace), which optimizes for same-identity embeddings to cluster and
different-identity embeddings to separate under cosine distance. Lightweight
architectures purpose-built for this (e.g. MobileFaceNet-scale heads,
~1M parameters) fit the "lighter is better" constraint directly.

### Training

The backbone is trained (or fine-tuned) with a combined objective:

```
L = L_detect + λ · L_ArcFace/CosFace
```

`L_detect` keeps the original detection performance intact. It includes a
distillation term against the original detector's outputs, which prevents
regressions while the backbone is adapted. `L_ArcFace` trains the embedding
head for identity separation.

There is a trade-off here. Features that are good for locating a face (edges,
coarse shape) are not automatically good for telling people apart (eyes,
nose, mouth). Sharing the backbone saves computing time but can cost some
accuracy compared with a separate ReID backbone, so this needs to be
measured, and λ needs tuning.

## Identity matching

Each embedding is compared via **cosine distance** against a gallery of
enrolled ("allow-listed") individuals' reference embeddings. A calibrated
threshold determines match/no-match.

The threshold should be tuned conservatively: a false match against the
allow-list means a person who should be anonymized is left visible, which
could have legal consequences. The system defaults to **blurring on
uncertainty**: no-match and low-confidence-match are both anonymized.

## Temporal efficiency: detect every frame, track, re-embed sparingly

Running the embedding head on every detected face on every frame is
wasteful once identity has already been established for a face currently
being tracked. Instead:

1. Detector (shared backbone) runs every frame, as required for anonymization
   regardless of identity.
2. A lightweight **SORT-style tracker** (such as a Kalman filter over bounding-box
   state) maintains per-face tracks frame-to-frame. It is computationally negligible
   next to a CNN forward pass.
3. The embedding head is invoked **conditionally**, only when:
   - a new track first appears (initial identity check against the gallery),
   - periodically, every *N* frames, to re-verify an existing track, or
   - a track is lost and needs to be recovered (occlusion, re-entry, ID
     switch). 

This keeps the always-on cost limited to detection + tracking (both cheap),
while the more expensive embedding computation only runs on the faces and
frames that actually need it. Even then, it reuses the shared backbone's
feature maps instead of paying for a second encoder.

## Privacy and compliance (EU AI Act / GDPR)

No embeddings or frames are persisted beyond the active processing window.
Matching is done in memory and discarded per frame/track. This reduces risk
but does not make the system exempt. Real-time matching of a detected face
against an enrolled gallery is still biometric identification processing
under GDPR and falls within the EU AI Act as high risk.

Practical implications for this design:

- The enrolled ("allow-list") individuals need a documented legal basis.
  Consent is the natural fit, since they are opting in to remain visible.
- Reference embeddings should be purpose-limited (used only for this
  matching, never repurposed) and treated as sensitive data while they
  exist, even transiently.
- Deployment context should be checked against the AI Act's risk tiers.
